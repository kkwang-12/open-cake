<a id="project-review--1-审查结论"></a>
## 1. 审查结论

**方案有条件可行，适合按单门店、原生小程序、云开发的 V1 分阶段实施；当前执行书更接近产品与 UI 总纲，尚不能直接作为完整工程执行合同。** 产品导航、视觉方向、购买主流程和领域划分清晰；真正需要补齐的是交易不变量、资源占用、外部支付接入、售后规则和可重复验收标准。

当前代码处于「旧预订演示 + 新首页视觉探索」并存状态。不能把现有演示支付替换成一个微信支付按钮就视为迁移完成。先统一数据模型和接口，再替换购买链路与订单规则，能降低返工风险。

|---|---|---|
| 产品与 UI | 可实施 | 保留四 Tab、黑白灰、独立配置页、三分类；实拍与中文信息仍待补齐 |

| 支付 / 退款 | 有外部前置条件 | 需确认 AppID 关联、商户能力、接入方式、通知与查单权限；本地配置不能证明已经开通 |

## 4. 建议的 V1 业务基线

以下为审查建议，尚未成为原执行书的正式业务决策。无须再次确认已有定稿的品牌、平台、四 Tab、三分类或视觉方向；新增政策按第 7 节在相应阶段冻结。

<a id="project-review--41-购买与金额"></a>
### 4.1 购买与金额

- V1 全额微信支付，一单可含多行商品；不迁入定金 / 尾款 / 线下尾款登记。
- 各金额均为人民币整数分：`subtotalCents = Σ(unitPriceCents × quantity)`；`totalCents = subtotalCents + deliveryFeeCents`。V1 无折扣、优惠券与额外隐藏费。
- 前端提交 SKU / 数量 / 留言、履约选择和幂等键；云端读取有效 SKU、校验所有权、配置版本和资源后计算金额。客户端总价仅展示。
- Checkout 报价有有效期与版本；报价不预留库存和名额。真正创建订单时复核，变化则要求用户重新确认报价，不默默按新价收款。
- 客户端重复点击、超时重试沿用同一请求键；同一用户同一键同一 payload 返回同一订单，不同 payload 返回冲突。
- V1 建议一个购物袋只结算一家门店，一单一个履约方式和时段。混合商品执行最严格的提前预约规则。

<a id="project-review--42-状态与资源"></a>
### 4.2 状态与资源

建议拆开持久化状态，展示层兼容执行书需要的异常态：

| 状态轴 | 建议枚举 | 规则 |
|---|---|---|
| `orderStatus` | PENDING_PAYMENT / PAID / ACCEPTED / MAKING / READY / DELIVERING / COMPLETED / CANCELLED | 仅受控领域命令迁移；READY 对配送表示待交给配送人员 |
| `paymentStatus` | UNPAID / PENDING / PAID / CLOSED / EXCEPTION | 未知或冲突进入 EXCEPTION 或待查，不从客户端判断成功 |
| `refundStatus` | NONE / PENDING / SUCCEEDED / FAILED | CANCELLED 订单可仍处于退款中；资金失败不伪造退款成功 |
| `reservationStatus` | HELD / CONFIRMED / RELEASED / CONSUMED | 资源释放 / 消耗一次，避免取消或回调重复退库存 |

自提：`MAKING → READY → COMPLETED`，完成来源为受权商家核销。配送：`MAKING → READY → DELIVERING → COMPLETED`，完成来源按冻结的商家 / 顾客确认规则决定。展示层可将 `refundStatus=PENDING` 显示为退款中、成功显示为已退款，但保留真实履约状态与日志。

订单创建事务预留 SKU 库存和时段名额，同时写订单、订单行、日志、幂等记录；付款确认后预留转确认。到期取消须先判断支付状态：未创建外部支付单可直接释放；已创建则查单 / 关单确认后再释放。遇到网络未知结果保持待处理，不提前开放同一资源。

已取消订单收到可信迟到成功通知：记录实际资金，进入退款补偿，不自动恢复履约。已制作 / 已消耗的原料不因退款自动恢复可售库存；取消时按资源状态和政策处理。外部支付或退款调用不放入数据库事务，采用独立持久化意图与重试补偿。

<a id="project-review--43-最小数据模型增补"></a>
### 4.3 最小数据模型增补

这是阶段二的设计起点，详细字段、索引、类型和权限应在 D02–D07 的 `DATA_MODEL.md` / `API_CONTRACT.md` 冻结；本次未创建集合。

| 模型 | 最小责任与关键约束 |
|---|---|
| 原有 users / categories / products / skus | 可信身份；固定三分类；商品 / SKU 版本、价格整数分、上架状态、库存与规格合法映射 |
| favorites | owner + product 唯一；商品下架仍可解释失效并取消收藏 |
| carts | 一用户一门店活动袋，包含稳定 lineId、SKU、逐行留言、数量、版本与勾选项；限制最大行数 / 数量 |
| addresses | owner、联系人、地区、详细地址、默认标记及可验证位置；默认地址更新需保证一致性 |
| stores / store_config | 门店资料、时区、营业 / 停业、提前量、预约窗口、时段容量、配送边界和费率版本 |
| checkout_quotes（建议增补） | owner、选中购物袋版本、金额明细、履约参数、过期时间；不代表库存预留 |
| orders / order_items / order_logs | 金额与状态、逐行商品快照、履约快照、version、actor / reason / 时间；用户与管理员读取隔离 |
| payments（必须增补） | orderId、唯一 outTradeNo、transactionId、金额 / 币种、状态、预支付与查单时间；重复回调不能重复入账 |
| refunds（必须增补） | 关联真实付款、唯一 outRefundNo、金额、状态、退款原因；累计退款不超过实付 |
| payment_events（必须增补） | 可信通知事件、处理状态 / 结果与业务去重键；不保存不必要的原始隐私数据 |
| reservations / slot_inventory（必须增补） | 资源数量与归属、过期及释放记录；slot 文档按门店 + 日期 + 时段定位，便于事务 doc 操作 |
| idempotency_records（建议独立） | owner + command + key 唯一，payload 摘要、结果引用；也可合并到对应业务实体并验证唯一性 |
| admin_roles / audit_logs（必须有等价实现） | 受控管理员授权 / 撤销；门店范围；角色、价格、状态和退款操作可审计 |

库存建议先按可售 SKU 数量维护，制作能力按时段最大订单数维护。这是两种资源约束；若门店按尺寸共用产能，应另冻结共享库存规则，不能假设每个口味有独立实物库存。

### 4.4 领域与阶段归属

用户要求的阶段顺序固定为：项目初始化 → 数据模型 → 商品域 → 购物袋 → Checkout → Order → Payment → Admin → 联调测试。

## 5. 技术接入核查

<a id="project-review--51-微信支付"></a>
### 5.1 微信支付

云开发可承载支付业务，但不等于现有 AppID 自动具备收款能力。当前 CloudBase 提供集成中心，可托管凭证及回调验签 / 解密；选用它仍需确认本项目账号、SDK、部署和回调信任边界。依据：[CloudBase 集成中心概述](https://docs.cloudbase.net/integration/introduce)、[集成使用流程](https://docs.cloudbase.net/integration/usage)。核查日期：2026-10-03。

I08 / P01 应记录选用“平台集成”或“云函数直接接微信支付 API”的单一方案，明确验签由谁承担、回调如何防伪、凭证如何保管。不要混用旧云支付参数与另一条 API 的通知格式，也不要直接信任可由顾客调用的函数参数。

微信支付官方要求结合通知与查单确认结果；因此本计划包含通知幂等、主动查单和未决资金补偿。[微信支付：支付回调和查单实现指引](https://pay.wechatpay.cn/doc/v3/merchant/4012075249)

<a id="project-review--52-数据库事务与运行时"></a>
### 5.2 数据库事务与运行时

CloudBase 事务文档将事务限定在服务端，并列出操作数、时长及 doc 操作约束；所以应限制购物袋规模、预先定位 SKU / slot 文档、控制事务范围，外部收退款调用另行补偿。具体 SDK 能力应在 I03 / D04 实测，不把示例代码视为所有 SDK 都可直接兼容。[CloudBase：事务操作](https://docs.cloudbase.net/database/transaction)

当前本地 Node 为 v24.19.0，项目要求 Node ≥22。云端运行时必须独立核验；不建议仅因为本机版本可运行就使用未验证的云 SDK 或 Node API。

## 6. 工作量和排期判断

按完整交付估算：**一名熟悉微信小程序与云开发的全栈工程师，约 51–79 人日（约 10–16 个工作周）**；属于任务规划量级估算，不是承诺工期。包括业务、自动化与真机验收，不含商户资质办理、审核等待、素材拍摄和未决规则的外部等待。支付集成及云资源费用另按实际账号套餐确认，本次不虚构预算报价。

| 阶段 | 估算人日 | 主要不确定性 |
|---|---:|---|
| 项目初始化 | 4–6 | 云权限、遗留路由迁移与工具配置 |
| 数据模型 | 4–6 | 状态 / 库存 / 索引与权限验证 |
| 商品域 | 6–9 | 正式商品资料、合法规格与 UI |
| 购物袋 | 4–6 | 并发版本、合并身份与失效行 |
| Checkout | 7–10 | 配送边界、时区、多商品提前量 |
| Order | 7–10 | 幂等下单、预留、取消竞争 |
| Payment | 8–13 | 商户接入、通知 / 查单 / 退款补偿 |
| Admin | 5–8 | 受控授权、核销和资源配置 |
| 联调测试 | 6–11 | 真机、异常、恢复与真实支付 |

不能将“无独立服务器”理解成“无后端工程量”。云开发减少基础设施维护，业务正确性仍需设计、实现和验证。多人实施可缩短部分页面工作，但数据模型 → Order → Payment 的依赖仍在关键路径。

## 7. 决策登记与停止点

这些问题不阻塞本次文档初始化；只阻塞明确依赖它们的业务 Task。文档内建议不能自动当作商家已同意的经营政策。

| 决策 | 当前建议 / 需提供资料 | 冻结前的最晚位置 |
|---|---|---|
| 交易与迁移 | 按执行书全额支付；旧演示订单仅保留回归，不导成真实订单 | D01，之后 O01 |
| 门店范围 / 库存 | 单门店 V1；SKU 可售数量 + 时段订单容量；确定是否共享库存 | D03–D05 |
| 真实商品 | 三分类产品、合法 SKU、价格、提前量、留言长度、数量上限、实拍图 | C01 / C03 |
| 门店营业 / 预约 | 门店时区、营业 / 停业、最短提前量、未来窗口、时段容量和未支付保留时长 | D05 / X02 / O03 |
| 配送 | 范围是行政区还是半径 / 多边形；地址定位来源、配送费、边界包含规则、人工配送责任 | X03 / X05 |
| 取消 / 拒单 / 售后 | 未付款可取消；商家无法接已付款单应退款；接单 / 制作后取消是否允许及如何审核 | D01 / O05 / P06 |
| 取餐核销 | V1 可先数字码；码长、有效期、尝试限制；二维码需同一凭证规则 | O07 |
| 配送完成 | 谁能确认、异常配送如何联系门店；暂不默认自动完成 | O08 |
| 支付能力 | AppID / 商户关联、可用接入路径、云权限、凭证与受控实付测试安排 | I08 / P01 |
| 管理员 | 初始管理员真实身份与门店权限；授权 / 撤销受控，不能自注册管理员 | A01 |
| 发布资料 | 真实门店地址 / 联系方式、隐私与售后文案、素材来源、客服入口、实际平台审核要求 | Q08 |

<a id="project-review--8-执行建议"></a>
## 8. 执行建议

先完成 I03 的云环境最小验证和 D01 的交易规则冻结，再推进数据模型。用阶段门禁限制依赖：报价可先验收，不能假装已经创建订单；订单域可用受控测试事件验收，不能把模拟事件开放给正式顾客；真实支付未通过前不开放营业。

本次新建工程规范和文档，未修改原执行书，也未删除旧演示或覆盖首页探索。所有尚未实现的能力在开发计划中保留待验收状态。
