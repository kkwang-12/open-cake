# 登录 UI v3 审查报告
日期：2026-10-06
对象：01-login-doubao-style-v3.png、login-v3-notes.md、当前小程序身份与路由实现。
范围：UI、交互与实施条件审查。未修改页面、配置、身份服务或既有设计提案；未部署或调用实际微信／短信服务。

## 结论
方向可以保留，四个页面／状态都可用常规小程序页面、弹层、输入与按钮实现。
当前稿是主流程概念，不宜直接作为实现验收稿：需要补充小屏／键盘、请求中／失败状态，并明确手机号在现有微信身份体系中的作用。
视觉原型可先完成；真实登录尚有账号初始化、云环境和短信链路的缺口。这些缺口不能用前端“登录成功”标记补齐。

## 必须明确的身份问题（高优先级）
### R01：手机号登录与现有账号模型不一致
证据：
- cloudfunctions/_shared/authorization-model.js:43 附近以 environment/appId/openId 派生稳定用户身份。
- docs/DATA_MODEL.md:84 的 users 定义及 docs/AUTHORIZATION-RULES.md:11 约定同一微信平台元组对应用户。
- 未发现独立手机号身份、手机号绑定／合并、短信登录会话的实际实现。
影响：
现有模型中订单归属依赖稳定用户 ID。若新增另一种独立账号来源而未定义映射，会产生两套账号／订单访问不同／登录方式切换后归属不一致的风险。界面看起来像两种等价登录，当前实现并没有这种语义。
建议：
先确定两种方案之一：
A. 保持微信平台身份为主，手机号是同一账号的绑定／验证；文案与说明如实表达。
B. 手机号作为独立登录凭证，先设计统一账号 ID、关联与冲突处理，再接短信登录；不按手机号字符串自动合并既有账号。
无论选择哪种，验证码通过不直接构成对任意订单的权限；业务仍核对服务端账号及所有权。
该问题需要用户确定业务方向，当前审查不擅自改登录入口。

### R02：微信身份检查不能代替完整业务登录
证据：
- miniprogram/services/user.js:2 只有 user.me。
- cloudfunctions/user/index.js:6–9 检查平台上下文，返回 authenticated、subjectHash 和 customer。
- cloudfunctions/_shared/api-contract.js:23–26 将 user.bootstrap/profile/consent 标记为默认 PLANNED。
- docs/API_NETWORK.md:243 明确 bootstrap 仅有契约，尚无写库实现。
- miniprogram/runtime-config.js:3–9 当前 shell 模式、各云环境为空。
- miniprogram/services/cloud.js:3 仅允许 user.me 和 store.health；shell 会在:11 拒绝云调用。
影响：
身份检查成功不证明业务账号已创建、协议已保存、昵称头像已取得、订单已授权，也不能拿 subjectHash 当用户主键。
建议：
定义明确完成条件：服务确认平台身份 → 真实初始化／读取业务账号 → 处理当前协议版本记录 → 页面更新并按原入口返回。具体同意持久化顺序须与用户服务契约一起落实，避免首次账号创建和 OWNER 同意接口互相阻塞。
云开发身份可来自云函数 getWXContext，无需为了按钮视觉额外设计第三方 OAuth 跳转。
今天可以做界面与交互原型；不伪造真实账号／登录结果。

### R03：短信与协议正文尚未接入
代码搜索未发现发送／校验验证码动作、短信服务实现和真实手机号登录接口。
未注册登录、手机号、验证码或独立协议正文路由（miniprogram/constants/routes.js:1–7、app.json）。
现有我的“隐私与服务说明”为准备中提示，未验证真实已发布正文。
建议：
短信发送、校验、发送频率、验证码有效期、失败次数限制与真正业务账号的映射由服务处理；客户端倒计时只用于交互。
协议／隐私链接需有实际阅读目标，不能用空链接；“首次登录自动创建账号”在真实初始化支持后才展示。
UI 原型将这些服务作为明确接口边界；原型不改变现有公共／本机页面访问。

## UI 需要调整／补齐（中优先级）
### R04：欢迎页在小屏上偏满
当前品牌字标、圆形蛋糕、主欢迎语、两按钮、协议、继续浏览纵向占用接近整屏。图中欢迎语为一行，但更窄屏或系统大字体可能换行，底部入口与安全区有冲突风险。
建议：
优先缩减品牌与蛋糕区高度和区间留白；蛋糕建议约160–210px弹性尺寸，不缩小主按钮／协议字体维持一屏。允许正常滚动，保持最后入口能滚到安全区上方。标题允许自然两行。
不按图中的固定纵坐标实现。

### R05：按钮形状与品牌名尚是概念值
当前图主按钮更像圆角矩形，现有 action-capsule 是58px高、29px圆角、18px/500、左右24px。参考豆包不自动授权重定义共享按钮。
建议：
落地复用 miniprogram/styles/action-capsule.wxss:2 的全圆角参数；新页表面暖白、字体按现有文字职责。若要采用图中较小圆角，应由用户明确提出后只在本页处理。
图中 LUNE 与当前家家乐品牌配置不同：素材可以继续作为提案；落地最终品牌名称待确认，不把示例字标写入全局。
顶部椭圆“…”为原生胶囊示意，不能额外实现一份假胶囊。返回／关闭使用44px触摸区与动态安全区。

### R06：手机号区号箭头制造了未定义入口
图中 +86 后出现下拉箭头，用户会预期可选择国家／地区，但现有草稿手机号规则按大陆格式。
建议：
若本期仅支持大陆，删除箭头，+86作为静态区号；若支持其他地区，需正式号码规则和短信能力后再放开。
初始输入为空，11位正确后获取验证码可用；图中示例号码不作为预填用户号码。
展示分组号码与实际数字值分离，避免空格占用长度／干扰光标。

### R07：键盘打开状态必须补图并真机核验
当前两张输入页未绘制键盘，不能证明真实编辑时排版可用。
建议：
手机号页获得焦点后号码区、获取验证码和相关错误可见；底部微信切换可随滚动进入或在键盘收起后展示，不硬固定在键盘背后。
验证码页使用一个真实数字输入承载六格，支持连续输入、退格、粘贴；六格按可用宽度等分，在窄屏保留间距，不硬编码固定总宽。
首格焦点来自真实输入焦点；键盘收起后不能继续显示误导性的输入光标。自动填充可作为增强，不能依赖其必然触发。
至少检查320/375/390/430逻辑宽度、较短屏、高字体、iOS和Android；视觉最终由用户真机确认。

### R08：缺少可审阅的请求／异常状态稿
说明已覆盖不少异常，四状态图尚没有具体布局。
建议补齐：
1. 手机号为空或格式错：按钮状态与就地错误。
2. 正在发送／发送失败／发送受限：保留号码、恢复方式明确。
3. 验证码验证中：输入状态和“正在验证…”位置。
4. 验证码错误／过期：文字提示、重新输入入口。
5. 网络失败：允许“重新验证”，不要反复自动发送。
6. 登录成功但账号信息加载失败：保留真实身份状态，可重试资料，不假装登录失败／清空资料。
7. 账号不可用：独立说明，不误报成“验证码错误”。
8. 协议阅读返回、关闭登录、直接打开无返回栈。
这些状态可在现有布局中放小号提示，不必增加大量独立页面。

## 交互需要修正／固化
### R09：协议确认时机建议调整
当前 v3 在点击“手机号登录”入口时就要求同意，尚未输入号码，增加一次导航阻碍。
建议：
- 手机号入口直接进入输入页；真正点击获取验证码时，如未同意再显示确认。
- 微信入口在执行业务登录前检查同意。
- 已在本次流程明确同意可沿用，图中手机号勾选状态只表示前一步用户同意，不能当首次默认。
- 切换方式、读协议返回不会重复弹窗或重发请求。
- 未同意也能关闭登录和继续公开浏览／本机地址管理。
这是对 v3 说明的审查建议，尚未自动替换其流程。

### R10：自定义协议与平台隐私流程需区分
自定义勾选和弹窗记录业务协议状态；若后续使用获取手机号等平台开放能力，需对应平台的用户触发和隐私授权流程。不能仅 setData 将勾选设为 true 后宣称平台授权完成。
当前仅从可信微信云上下文识别调用方，不等于需要强制头像／昵称／手机号授权。
建议：
按实际启用能力设计一次连贯流程，避免自定义弹窗与平台授权重复且不明确；平台授权被取消时留在当前页面，说明真实原因。
协议正文／版本与账号记录、平台状态分别处理。本报告不代替微信后台能力开通及正式隐私资料审核。

### R11：返回、重发与自动校验需要完整规则
- 手机号分支：填写手机号 → 发送成功 → 六格验证码 → 完成后只提交一次校验 → 服务确认账号状态 → 返回原入口。
- 微信分支：业务协议 → 平台身份／账号服务 → 返回原入口；不强制走短信步骤。图板底部单线仅代表手机号分支。
- 完成六位自动验证可以保留，但请求中锁定重复提交；错误／超时有恢复操作。
- 倒计时归于当前号码与当前发送结果；重发成功绑定新验证过程，不能使用旧过程完成新请求。
- 换号／返回／关闭后，旧异步响应不能再次跳转或改新页面。返回前校验当前流程仍有效。
- 登录返回订单等导航页复用 switchTab；普通详情页可 navigateBack；不能对所有来源统一navigateTo或堆叠登录页。
- 原入口已失效或无返回栈回我的；取消不恢复原受限动作。
- 登录成功只返回原页面或恢复无副作用的访问，不自动下单／支付／删除。
- 用户退出是产品登录态变化，不代表微信平台身份消失；业务访问策略仍应服务端定义。

## 建议的今天交付边界
保持这套极简风格，先形成登录 UI 实施稿：三页（欢迎／手机号／验证码）加协议弹层、上述关键状态、键盘和小屏适配说明。
身份来源与账号映射确定后再定最终入口文案；微信登录／短信／账号初始化接入另按实际配置核验。
本轮审查不新增页面或测试，只读取代码与图稿并形成报告；没有真实微信、短信、账号持久化或真机验证。
